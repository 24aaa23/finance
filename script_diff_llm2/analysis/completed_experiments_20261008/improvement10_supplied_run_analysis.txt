## 01Key findings

1. **The pipeline is reliable but not yet accurate on analytical questions.** All 6,954 model calls succeeded and 990 of 1,000 questions executed end to end. Accuracy, though, ranges from 96% on lookup-style suites (Benchmark, Batch Status) to 61.6% on Multi-Step Comparative.
2. **Most errors are semantic, not crashes.** Only 10 of 161 non-matches are pipeline errors. The other 151 are confident wrong answers: wrong aggregation grain, dropped filters, NULL-group handling, or the wrong source column.
3. **One inconsistent NULL policy causes 28 failures on its own.** The pipeline drops NULL groups in GROUP BY answers, where the ground truth keeps them, and it adds NULL rows to reference-value lists, where the ground truth excludes them. It gets both cases backwards. Query Understanding leaves `null_policy` “unspecified” in 450 of 1,000 questions.
4. **A contract-check repair silently drops filters.** When the checker says a predicate “moves downstream” and forces regeneration, the filter is sometimes never re-applied. Six different temporal questions returned the identical unfiltered table total (2,110,617,425), and two date-count questions both returned the full row count (7,828). That accounts for 8 of the 11 Temporal-suite mismatches.
5. **Accuracy falls with join depth and nested aggregation.** Accuracy is 93.4% with 2 tables, 78.9% with 3 and 72.0% with 4. Questions that need a per-investor aggregate before a group average (Multi-step Comparative, Composite Reasoning) are the weakest query types at 56–78%.
6. **Retries and repairs predict failure.** Questions that used all three Final_Spec attempts score 38.9%, and questions with 4+ repairs score 42.9%, against 85.5% with no repairs. The slowest latency quintile (over 68 s) scores 69.5%, against 84–92% for the rest.
7. **The grader is useful but inconsistent at the margins.** The same defect (duplicate rows, an extra NULL row, a superset of IDs) is graded MATCH in some questions and PARTIAL or MISMATCH in others. Strict accuracy probably carries a few points of grader noise in both directions.
8. **Fixing four mechanical issues could lift strict accuracy to about 89%.** The four are the NULL policy, dropped filters, Final_Spec grain errors and duplicate rows from joins. Together they cover 54 of the 161 non-matches. Deeper gains need better handling of nested aggregation grain.

## 03Trends

### Complexity: tables joined

Bars: strict accuracy. Line: median seconds per question. Number of tables correlates with model calls (ρ = 0.84), input tokens (0.78) and latency (0.69).

Cost rises steadily with each extra table. Accuracy does not fall steadily: it peaks at 2 tables (93.4%), drops at 3–4, and recovers at 5 (84.4%).

The single-table dip (84.4%) is not about joins. Those questions are mostly large filtered lists and reference-value counts, where row completeness and NULL handling are judged strictly. The 5-table recovery comes from formulaic "five-signal" detection questions (20/20 correct) that are easier than their table count suggests.

Answer size matters too. Single-row answers are 94.6% correct, but answers with 2–5 rows (typically small GROUP BY results) drop to 71.4%. That is where missing NULL groups and wrong group averages show up.

### Query type

Sorted by strict accuracy. The gap between the two bars is PARTIAL credit. Reference Compliance and Multi-step Comparative have the largest gaps: their answers are mostly right with one systematic defect.

### What each failure looks like

| Cause | Example | Mechanism |
| --- | --- | --- |
| Aggregation grain | MC125-040 | "Average rebalance amount" by risk tolerance. Ground truth averages each investor's *total* (about 405k). The pipeline averages individual rows (about 89k). The same pattern drives the "average signed cash-flow amount" and "average total holding value" errors across Multi-step. |
| NULL policy | RC125-011 · EC125-2T-003 | Reference-value listings add a `null → 77` row that the ground truth excludes with `IS NOT NULL`. GROUP BY answers drop the `risk_tolerance = null` group that plain SQL keeps. |
| Dropped filter | TT125-025 · TT125-041 | The Query_Spec contract check rejects a predicate placed at retrieval ("moves downstream predicate into raw retrieval"). After regeneration, Final_Spec never applies it, and the result is the whole-table sum or count. |
| Wrong source column | EC125-2T-043 | "Category" is bound to `PORTFOLIO_HOLDING.category` (15 asset categories) instead of `INVESTOR_PROFILE.category` (5 investor categories), because two tables share a column name. |
| Spec error | MC125-091 · SQA125-3T-001 | 8 of 10 hard failures hit the guard "final aggregate grouping differs from interpreted output grain", 3 of them together with join-arity or dataset-name errors (`left_on/right_on requires exactly two datasets`). The other two are an invalid expression and a lost outer COUNT. |
| Ranking drift | MC125-110 · MC125-084 | Top-10 composite rankings get 8–9 of 10 right. One component (often the holding gain filter or the min-max normalisation population) differs slightly, which swaps the 10th investor. |
| Fan-out duplicates | WM125-3T-020 | Joining to sector allocations without DISTINCT repeats investors (INV-665, INV-759) who appear in more than one qualifying row. |

- **Query Understanding is the most expensive stage**, at 39% of LLM time and 34% of tokens. Its prompt is about 86k characters, mostly static schema and business-rule context, and 28% of questions call it more than once.
- **Prompt caching is barely used.** Cached-token usage was reported for only 308 of 1,000 questions, covering 7.7 M of 92 M input tokens (8.4%). The static Query Understanding prefix is an obvious caching candidate.
- **Wall-clock time:** the eight suites ran in parallel, one worker each. The full run took 3 h 05 m, bounded by Multi-Step Comparative (11,109 s). Serial time would have been 14.0 h.
- **Failures cost more.** MATCH answers median 40.6 s and 86 k input tokens. PARTIAL answers median 57.4 s and 103 k. Multi-step needs 220 k tokens per correct answer, against 96–98 k for the easier suites.

## 06Grader reliability

Every question was graded once by gpt-5-mini in "direct semantic judgment" mode, with no deterministic check. Cross-checking its verdicts against a programmatic comparison of the result sets found these inconsistencies:

| Same defect | Graded MATCH | Graded lower |
| --- | --- | --- |
| Extra NULL row in a value listing | 2 (RC125-047, -050) | 14 PARTIAL |
| Exact duplicate rows in output | 5 | 8 PARTIAL 1 MISMATCH |
| Superset of required IDs | ARC125-4T-005 (53% precision) | ARC125-3T-004 (1 extra ID) → PARTIAL |
| Wrong ID column (portfolio_health_id instead of investor_id) | ARC125-1T-010, -011 | ARC125-1T-009 → MISMATCH |

On entity-ID answers (449 questions), MATCH verdicts average 98% ID recall and 98% ID precision, so the grader is right in the large majority of cases. The inconsistencies sit in the boundary cases, and each could move a question between MATCH and PARTIAL. The 19 questions with an empty ground truth were all answered correctly, but an empty answer passes those by default, so they add little signal.

## 07Limitations

### Of the pipeline

- No explicit NULL-group policy. GROUP BY and distinct-value questions are handled in opposite ways.
- Nested aggregation ("per investor, then across investors") is the weakest capability. It drives most Multi-step and Enrichment errors.
- Column binding is ambiguous when tables share names (`category`, `segment`, `sector`).
- Repair loops can delete constraints. A repair that drops a filter returns a plausible but wrong number with no warning.
- The `agent_consultation` feature is enabled but recorded 0 consultations. The QU `ambiguities` field was empty for all 1,000 questions, so neither safeguard ever fired.
- Heavy token use: about 98 k tokens and 7 LLM calls per question, even for single-row lookups (about 64 k).

### Of this evaluation

- There is no baseline. "Old Status" is `NEW_BENCHMARK` for all rows, so this run cannot show improvement over a previous version.
- Grading uses one LLM judge in a single pass, with the inconsistencies shown above. There is no execution-equivalence or exact-match metric alongside it.
- The suites have 125 questions each, so differences between suites under about 8 points are within noise.
- Difficulty labels are not comparable across suites, and query type, table count and suite are confounded with each other.
- Ground-truth conventions vary: some include NULL groups and others exclude them by design. The pipeline cannot infer which convention a question expects from its wording.
- The data is one synthetic wealth-management SQLite database, with one model and one seed, so results may not transfer to other schemas.

## 08Recommendations, in priority order

| Fix | Questions affected | Effort |
| --- | --- | --- |
| **Explicit NULL policy.** Keep NULL groups in GROUP BY output by default. Exclude NULL from "values in use" and distinct-value listings unless the question asks for them. | 28 (+11 partial) | low |
| **Predicate-preservation check.** After any repair, assert that every predicate from Query Understanding is applied somewhere in the final plan. Fail loudly if one is missing. | 10 | low |
| **Grain guard repair.** When "aggregate grouping differs from output grain" fires, regenerate with the expected grain stated in the prompt instead of failing. Also fix join-arity validation. | 10 | medium |
| **De-duplicate entity lists.** Apply DISTINCT on the entity key when the requested output is a list of entities. | 7 | low |
| **Disambiguate shared column names** in the knowledge pack. For example, "investor category" and "holding category" become separate concepts with distinct descriptions. | 10 | medium |
| **Nested-aggregation templates.** Add an explicit "aggregate per entity, then across entities" operator pattern, with tests on Multi-step questions. | 40–55 | high |
| **Confidence routing.** Flag answers with 3 Final_Spec attempts, 4+ repairs, or more than 10 calls. This catches 12 of the 54 mismatches. | 46 flagged (65% match) | low |
| **Cache the static QU prefix** and cut repeated QU calls. | cost only | low |
| **Make grading deterministic first.** Run an order-insensitive result-set comparison with numeric tolerance, and use the LLM judge only for questions where the comparison disagrees or cannot decide. | eval quality | medium |

If the first four fixes each converted their affected questions to MATCH, strict accuracy would rise from 83.9% to about 89%. That is an upper bound. Each fix will likely recover most, not all, of its cases.

Method: graded CSVs, debug CSVs, input question files and per-call telemetry from all eight suite folders were merged on question ID. Root causes were assigned from grader rationale, programmatic result-set comparison (entity-ID recall and precision, numeric matching within 0.5% tolerance, NULL-row and duplicate detection) and debug traces (repair logs, final specs, scan summaries). Confidence intervals are Wilson 95%.
